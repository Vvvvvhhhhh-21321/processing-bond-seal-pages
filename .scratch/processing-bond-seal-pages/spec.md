# 债券底稿盖章页两阶段处理规格

Status: ready-for-agent

## Problem Statement

债券项目组需要从大量 Word 底稿中逐份取出最后一页，合并成可发送给客户的待盖章页合集；客户盖章后返回的 PDF 可能乱序、缺页或为纯扫描件，项目组还需要把每张回章页重新匹配并替换回对应底稿。现有流程依赖人工转换、拆页、辨认、回拼和核对，数量大时耗时且容易错页。

当前仓库已有标题归一化与模糊匹配、日期落位、PDF 抽取合并与回拼、表格页识别等底层代码，但技能说明仍是模板，没有 Word 转换、OCR、处理批次、两阶段编排及最终处理清单。现有回拼还会拉伸页面，标题匹配只有单一阈值，均不符合已确认的业务规则。

## Solution

提供一个面向债券底稿文件的通用 Skill，将业务拆分为两个明确阶段。

第一阶段接收一批 `.doc` 或 `.docx` 底稿文件，在 Windows 使用 Microsoft Word、在 macOS 使用 LibreOffice 转为完整 PDF，从每份底稿中提取最后一页，按文件逐页生成不去重的待盖章页合集，并保存完整 PDF、页面映射和校验信息作为处理批次。

第二阶段接收该处理批次、客户返回的回章页合集和可选的统一落款日期。系统优先读取 PDF 文字层，必要时使用本机 RapidOCR 与 PP-OCRv6 `small` 做中文 OCR；随后按标题独立匹配乱序页面。高置信度项目自动完成日期补齐和最后一页原样替换，低置信度、歧义、缺页及失败项目跳过但不阻塞整批处理。最终输出逐份完整盖章版 PDF 和一个自包含、可筛选的 HTML 处理清单。

## User Stories

1. 作为债券项目组成员，我希望一次选择一批底稿文件，以便批量准备客户盖章材料。
2. 作为债券项目组成员，我希望同时处理 `.doc` 和 `.docx`，以便兼容历史底稿和新底稿。
3. 作为债券项目组成员，我希望当前版本只处理底稿文件，以便先稳定解决规则明确的场景。
4. 作为债券项目组成员，我希望系统把每份底稿的最后一页视为唯一盖章页，以便无需逐文件指定页码。
5. 作为纸质底稿整理人员，我希望同标题底稿的盖章页也全部保留，以便客户返回足够数量的纸质盖章页。
6. 作为债券项目组成员，我希望 Word 转 PDF 后保留完整 PDF，以便回拼时不需要再次转换 Word。
7. 作为债券项目组成员，我希望单个 Word 转换失败时其他文件继续处理，以便一个坏文件不阻塞整批任务。
8. 作为债券项目组成员，我希望第一阶段生成待盖章页合集，以便将一个 PDF 直接发送给客户。
9. 作为债券项目组成员，我希望第一阶段保存底稿、标题、合集页码和校验信息之间的映射，以便第二阶段可靠追溯。
10. 作为债券项目组成员，我希望两个阶段通过同一个处理批次衔接，以便避免重新转换造成分页变化。
11. 作为债券项目组成员，我希望客户回传页面可以乱序，以便无需客户维持原始装订顺序。
12. 作为债券项目组成员，我希望客户可以只返回部分页面，以便先处理已完成盖章的底稿。
13. 作为债券项目组成员，我希望缺失页面只影响对应底稿，以便其余底稿仍能生成盖章版 PDF。
14. 作为债券项目组成员，我希望系统优先使用 PDF 自带文字层，以便在可直接提取文字时提高速度。
15. 作为债券项目组成员，我希望纯扫描 PDF 自动使用中文 OCR，以便扫描回章页也能匹配。
16. 作为债券项目组成员，我希望 OCR 只用于识别与定位，不改变回章页图像，以便保留客户返回原件。
17. 作为债券项目组成员，我希望系统优先读取书名号中的标题，并在缺少书名号时尝试主要标题，以便兼容常见底稿格式。
18. 作为债券项目组成员，我希望无可识别标题的页面不按顺序猜测，以便避免乱序情况下错拼。
19. 作为债券项目组成员，我希望只有高置信度标题匹配才自动回拼，以便控制正式底稿的错页风险。
20. 作为债券项目组成员，我希望低置信度、歧义和未匹配项目被跳过但不中断批次，以便最后统一核对。
21. 作为债券项目组成员，我希望同标题页面优先逐页使用，以便尽量保留客户实际返回的每张纸质页面。
22. 作为债券项目组成员，我希望同标题回章页数量不足时允许复用，以便数字版底稿仍可完成回拼。
23. 作为债券项目组成员，我希望可为整个批次提供统一落款日期，以便批量补齐空白日期。
24. 作为债券项目组成员，我希望页面已有的年、月或日保持不变，以便不覆盖客户或项目组已填写的信息。
25. 作为债券项目组成员，我希望日期无法安全落位时保留原页并在清单中提示，以便回拼本身仍可继续。
26. 作为债券项目组成员，我希望回章页作为 PDF 页面对象原样替换最后一页，以便不拉伸、缩放或裁切印章。
27. 作为债券项目组成员，我希望原 Word 永远不被修改，以便保留可编辑源文件。
28. 作为债券项目组成员，我希望再次运行时覆盖旧生成结果，以便输出目录始终保留最新结果。
29. 作为债券项目组成员，我希望最终得到逐份完整盖章版 PDF，以便直接归档和提交。
30. 作为债券项目组成员，我希望获得一个自包含 HTML 处理清单，以便无需 Excel 即可快速打开核对。
31. 作为债券项目组成员，我希望处理清单能按成功、低置信度、未匹配、缺页、转换失败和日期失败筛选，以便集中处理异常。
32. 作为债券项目组成员，我希望清单显示原文件、合集页码、回章页码、标题、相似度、日期结果、状态、原因和输出位置，以便完整追溯。
33. 作为债券项目组成员，我希望清单不生成页面缩略图并提供本地文件位置或链接，以便减少处理资源和清单体积，发现问题后直接打开对应文件核对。
34. 作为债券项目组成员，我希望系统不判断是否盖章或印章真伪，以便功能边界保持在页面处理而非合规鉴定。
35. 作为 Windows 用户，我希望系统调用本机 Microsoft Word 转换底稿，以便尽量保持复杂 Word 版式和分页。
36. 作为 macOS 用户，我希望系统调用 LibreOffice 无界面转换底稿，以便在非 Windows 机器上完成同一流程。
37. 作为使用 Anaconda 的用户，我希望系统能识别当前 Conda 环境，以便复用我现有的 Python。
38. 作为普通 Python 用户，我希望系统能识别系统 Python、启动器和当前执行环境，以便不依赖固定路径。
39. 作为一台存在多个 Python 的机器的用户，我希望系统优先当前激活的 Conda 环境，其次当前执行环境，并在仍有歧义时让我选择，以便依赖安装到正确位置。
40. 作为环境尚未准备好的用户，我希望系统清楚列出缺失的 Python、转换器、依赖或 OCR 模型，并在我同意后帮助安装，以便顺利完成前置配置。
41. 作为环境维护者，我希望系统不静默创建回退环境或修改多个 Python，以便环境变化可见、可控。
42. 作为后续开发者，我希望当前底稿流程与未来发行文件流程有清晰边界，以便以后增加多签字页能力而不破坏现有流程。

## Implementation Decisions

- 系统提供两个独立的顶层工作流：准备处理批次，以及使用处理批次完成回拼。两个工作流也是最高层测试接缝。
- 当前业务类型固定为底稿文件；每份底稿文件仅有一个盖章页，且盖章页固定为最后一页。
- 输入支持 `.doc` 与 `.docx`。不直接修改 Word，所有后续操作以第一阶段转换得到的完整 PDF 为准。
- Windows 转换适配器使用 Microsoft Word；macOS 转换适配器使用 LibreOffice 无界面模式。转换器通过统一接口隔离，便于以后扩展其他平台。
- 第一阶段生成处理批次。处理批次至少保存完整底稿 PDF、待盖章页合集、源文件标识、相对位置、规范化标题、合集页码、页数和文件校验值。
- 待盖章页合集按底稿逐份收录盖章页，同标题页面不去重。
- 第二阶段不得重新转换 Word；处理批次中的完整 PDF 是回拼基准。
- 回章页匹配不依赖页面顺序，必须支持乱序和缺页。
- 标题识别优先使用 PDF 文字层；文字层不存在或内容不足时使用 RapidOCR。
- OCR 引擎采用 RapidOCR、ONNX Runtime 和 PP-OCRv6 `small` 中文模型，本机运行，OCR 结果不写回 PDF。
- 标题优先取书名号内容；没有书名号时提取主要标题，并可使用第一阶段记录的原文件名辅助校验。
- 标题比较执行 Unicode 兼容归一化，并忽略空白和标点差异。
- 自动回拼阈值设为相似度不低于 90。低于阈值、候选歧义或无法识别标题的页面不自动回拼。
- 低置信度或未匹配项目不触发中间人工确认；系统跳过该项目并继续整个批次，最终集中写入处理清单。
- 同标题底稿优先与同标题回章页逐页配对；回章页数量少于底稿数量时，允许复用已匹配的同标题页面。
- 系统不检测页面是否真实盖章，也不判断印章真实性。
- 回拼通过删除完整底稿 PDF 的最后一页并插入回章页原始页面对象完成。不得缩放、拉伸、裁切或重新栅格化回章页；结果允许最后一页尺寸与前文不同。
- 用户可以为第二阶段提供统一落款日期。页面已有日期组成部分优先，只补空缺的年、月或日。
- 日期补齐应避免覆盖已有内容；无法安全落位时不写入该日期组成部分，并将结果写入处理清单，但不阻止已匹配页面回拼。
- 单文件转换、OCR、匹配、日期或 PDF 写入失败不得终止其他文件处理。
- 输出包括逐份完整盖章版 PDF 和一个自包含 HTML 处理清单。HTML 支持状态筛选、关键字段展示和本地文件链接，但不生成页面缩略图。
- 再次运行可以覆盖同一输出位置中的旧生成结果，但绝不覆盖或修改原 Word。
- 前置检查动态发现系统 Python、Python 启动器、当前 Conda/Anaconda 环境和当前执行环境，不写死解释器或应用程序路径。
- 多个 Python 同时可用时，优先当前激活的 Conda 环境，其次当前执行环境；仍有歧义时由用户选择。
- 系统只检测前置条件、解释缺失项并在获得用户同意后帮助安装，不自动创建私有回退环境，也不静默向多个 Python 安装依赖。
- OCR 模型完成首次准备后应可离线复用。
- 现有表格页识别能力保留为未来发行文件扩展基础，但不接入当前底稿工作流。

## Testing Decisions

- 测试只断言用户可观察行为，不依赖内部函数调用顺序、具体 OCR 中间结构或转换器实现细节。
- 第一条最高层端到端接缝覆盖“底稿目录 → 处理批次”：给定包含 `.doc`、`.docx`、重复标题和转换失败文件的固定样本，断言完整 PDF、逐页不去重的待盖章页合集、映射、校验信息和状态均正确。
- 第二条最高层端到端接缝覆盖“处理批次 + 回章页合集 + 日期 → 盖章版 PDF + HTML 清单”：给定乱序、缺页、同标题数量不一致、扫描页、低置信度页和部分已有日期的固定样本，断言高置信度项目完成、低置信度项目跳过、同标题复用正确、日期按规则补齐、整批不中断且 HTML 信息完整。
- PDF 回拼测试必须断言回章页对象被原样插入，页面尺寸、方向和内容不因目标页尺寸变化而拉伸；前文页面保持不变。
- 标题测试延续现有归一化、书名号提取、模糊匹配、全局最优分配和同标题复用案例，并新增 90 分自动阈值、歧义跳过、无标题跳过及乱序缺页案例。
- OCR 适配测试使用固定图片和可替换引擎边界，验证文字层优先、OCR 回退、PP-OCRv6 `small` 配置和识别失败状态；常规单元测试不重复下载模型。
- 日期测试延续现有组成部分保留、空缺补齐、碰撞缩放和无法落位跳过案例，并验证日期失败不阻止页面回拼。
- 转换器契约测试对 Windows Word 与 macOS LibreOffice 使用相同输入输出行为断言；平台真实应用调用作为对应系统上的冒烟测试，不要求另一平台运行不可用的应用。
- 环境预检测试覆盖系统 Python、当前 Conda、多个候选、缺少 Python、缺少转换器、缺少依赖和用户拒绝安装等情形。
- HTML 处理清单测试验证状态筛选所需数据、路径、相似度、日期结果、错误原因和本地文件链接均完整，确保报告无需联网即可打开且不嵌入页面图片。
- 批次测试验证第二阶段复用第一阶段 PDF，不重新转换 Word；校验信息不一致时必须显式失败或跳过相关项目。
- 现有测试作为标题、日期、表格识别与 PDF 操作的先例。当前因新版 `pypdf` 字典键类型要求导致的测试夹具错误应先修正，再作为回归基线。

## Out of Scope

- 发行文件及一份文件包含多张签字页或多张盖章页的处理。
- Linux 平台的 Word 转 PDF 支持。
- 修改、覆盖或回写原始 `.doc`/`.docx`。
- 识别印章真伪、检查是否已盖章、检查盖章主体或执行合规判断。
- 低置信度项目的处理中交互式人工确认。
- 依赖客户按第一阶段顺序返回页面。
- 对无标题回章页按位置或顺序进行猜测匹配。
- 为了统一页面尺寸而缩放、拉伸、裁切或重新生成回章页。
- 自动创建私有 Python 回退环境或未经同意修改用户的 Python/Conda 环境。
- 将大型 OCR 模型二进制直接提交到 Skill 仓库。

## Further Notes

- 规格中的“处理清单”统一指自包含 HTML 报告，不指 Excel 文件。
- HTML 清单承担批次完成后的集中复核职责；流程中间不暂停等待人工选择。
- 当前代码中的同标题复用方向符合业务，但第一阶段不得据此去重待盖章页。
- 当前 PDF 回拼的非等比例缩放实现与本规格冲突，实施时必须改为原始页面对象替换。
- 当前单一 80 分阈值与本规格冲突，实施时必须改为 90 分自动阈值，并为低置信度和歧义结果保留明确状态。
- RapidOCR 官方模型列表显示 PP-OCRv6 提供 `tiny`、`small` 和 `medium`，本规格明确选择 `small`。
